ARTIKULA — Project Structure & Stack

What every technology is, what every file does, and how they connect

Part 1 — The Tech Stack

PHP — the programming language PHP is the language the backend is written in. It runs on the server. When a request arrives (e.g., POST /api/login), the server executes PHP code, talks to the database, and returns a response. PHP is the oldest and most widely-deployed server-side language on the web — it powers WordPress, Wikipedia, Facebook's original codebase. Version 8.5 (via Laravel Herd) is used here.
Laravel — the PHP framework Laravel is a set of pre-built tools and conventions for building web applications in PHP. Instead of writing raw PHP from scratch (connecting to MySQL manually, validating input by hand, generating HTTP responses), Laravel provides: routing, request validation, ORM, authentication, sessions, testing infrastructure, and much more. Think of it as the scaffolding. Version 13 is used here.
Composer — PHP package manager Composer downloads and manages PHP libraries. Like npm for Node or pip for Python. When you run composer install, it reads composer.json and downloads all listed packages into the vendor/ folder. composer.lock locks exact versions so every developer gets the same code.
MySQL — the relational database MySQL stores the persistent data: users, appointments, services. Data is organized in tables with rows and columns — like spreadsheets that are connected to each other via foreign keys. The application talks to MySQL via Laravel's Eloquent ORM. Version 9.6 (via Homebrew) is used here.
Laravel Sanctum — the authentication library Sanctum is a Laravel package that handles login sessions. In SPA (stateful) mode — the mode used here — it works via cookies: the browser gets a laravel_session cookie on login, and sends it automatically on every subsequent request. No API tokens needed. The XSRF-TOKEN cookie is the CSRF protection layer on top.
Eloquent ORM — the database abstraction layer ORM stands for Object-Relational Mapper. Eloquent lets you work with database records as PHP objects instead of writing raw SQL. Appointment::where('user_id', 1)->get() is Eloquent — it generates SELECT * FROM appointments WHERE user_id = 1 behind the scenes, as a PDO prepared statement (SQL injection safe).
PHPUnit — the testing framework PHPUnit runs automated tests. Laravel wraps it with helpers like postJson(), actingAs(), and assertStatus(). Tests run against a temporary in-memory SQLite database — they never touch your MySQL data. The command is php artisan test.

Part 2 — Request flow

What happens when the browser sends a POST to /api/appointments:

1
public/index.php — entry pointLaravel boots from this single file. Every HTTP request — no matter the URL — arrives here first. It loads the framework and hands control to the router.
2
bootstrap/app.php — middleware stack appliedSanctum stateful middleware checks: does this request have a valid session cookie? If no session, 401. If yes, the authenticated user is loaded. CSRF token is validated here too.
3
routes/api.php — route matchedThe router checks: which controller method handles POST /api/appointments? Answer: AppointmentController@store. Also checks throttle limit here.
4
Requests/StoreAppointmentRequest.php — validationBefore the controller runs, the Form Request validates every field. Date in the past? Reject. Time not in the list? Reject. Slot already taken? Reject. More than 3 appointments? Reject. If anything fails → 422 JSON response is sent back immediately.
5
Controllers/AppointmentController.php — business logicThe store() method runs. It calls Appointment::create([...]). Done.
6
Models/Appointment.php — Eloquent writes to MySQLThe model translates the PHP object into an INSERT SQL statement and executes it via PDO. The new record is returned.
7
JSON response sent back to the browserreturn response()->json($appointment, 201) — the new appointment is serialized to JSON and sent back with HTTP 201 Created.

Part 4 — Folder roles in one sentence each

Folder / FileRole
app/Http/Controllers/Receive the request, call the model, return the response. Keep thin — no business logic here.
app/Http/Requests/Validate every incoming request before the controller sees it. If invalid, 422 is returned automatically.
app/Models/Each class represents one database table. All database reads and writes go through here.
app/Policies/Authorization rules — "can this user do this action on this resource?" Called automatically by $this->authorize().
bootstrap/app.phpApplication configuration: which middleware to apply, how to handle exceptions.
config/Framework settings for database, sessions, mail, etc. Read-only at runtime.
database/migrations/Version-controlled history of the database schema. Run with php artisan migrate.
database/seeders/Insert initial/test data into the database. Run with --seed flag on migrate.
database/factories/Fake data generators for tests only. Used by User::factory()->create() in PHPUnit.
public/The only folder the web server exposes. All browser-accessible files (HTML, JS, CSS) live here.
routes/api.phpDefines every API endpoint: URL, HTTP method, which controller handles it, which middleware applies.
storage/logs/Log files written by the app at runtime. laravel.log captures errors and security warnings.
tests/Feature/Automated integration tests. Each test simulates a full HTTP request and checks the response and database state.
vendor/All downloaded Composer packages (Laravel, Sanctum, PHPUnit…). Ignored by git. Recreated by composer install.
.envEnvironment-specific secrets: database password, app key, domain config. Never committed to git.
composer.lockExact versions of every package. Committed to git — ensures reproducible builds on every machine.
phpunit.xmlPHPUnit configuration: which database to use for tests, env variable overrides (SQLite, BCRYPT_ROUNDS).

Part 5 — What is NOT in this project but is normally in Laravel

A standard Laravel app has more features. We deliberately left these out because they were not needed:

FeatureWhy we skipped it
Blade templates (resources/views/)Frontend is plain HTML in public/ — no server-rendered templates needed
Vite / Node.js build stepNo JS bundling — frontend uses vanilla JS + CDN jQuery, no npm run build
Queue & jobs (database/jobs)No background tasks in this project
Email sendingNo email_verified_at — registration does not require email verification
API tokens (Bearer tokens)Using cookie-based Sanctum SPA instead — more appropriate for a browser frontend
Role / permissions systemSingle user type — no admin, no roles needed

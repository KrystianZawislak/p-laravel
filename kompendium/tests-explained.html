Part 1 — Key concepts

Cookie A small piece of data the server sends to the browser, stored automatically. On every subsequent request the browser attaches the cookie back to the server — without the user doing anything. Used for sessions (knowing who is logged in) and CSRF tokens.

Example — server response header:
Set-Cookie: XSRF-TOKEN=abc123; Path=/; SameSite=Lax
Set-Cookie: laravel_session=xyz789; HttpOnly; Path=/
Session Laravel creates a unique session for each visitor and stores a session ID in a cookie (laravel_session). The actual session data (who is logged in) lives on the server. The cookie is just an ID — like a locker key, the locker with your data is on the server side.
CSRF — Cross-Site Request Forgery An attack where a malicious website tricks your browser into sending a request to a different website while you are logged in there. Example: you are logged into your bank, you visit an evil site — it silently sends a POST to your bank's "transfer money" endpoint using your session cookies.

How Laravel prevents it: The server generates a secret token (XSRF-TOKEN) and puts it in a cookie. Any POST/PUT/DELETE request must also send this token in a header (X-XSRF-TOKEN). An evil website can read your cookies via JavaScript only if it's on the same domain — so it cannot steal the token. Laravel rejects any state-changing request that does not include the correct token.
XSRF-TOKEN vs laravel_session
CookieWhat it storesWho reads itHttpOnly
XSRF-TOKENCSRF protection tokenJavaScript reads it, sends as headerNo — intentionally readable by JS
laravel_sessionSession IDBrowser sends it automaticallyYes — JS cannot read it (more secure)
Sanctum SPA (Stateful API) Laravel Sanctum in SPA mode uses cookies instead of API tokens. The frontend (browser) logs in once, gets a session cookie, and every subsequent API request is authenticated automatically because the browser sends the cookie. No need to store a token in localStorage. This is the approach used in ARTIKULA.

Part 2 — Manual terminal tests (curl)

These are the tests we ran manually in the terminal to verify the API works before writing automated tests. Every curl command is an HTTP request sent from the terminal.

The XSRF flow — step by step

Every state-changing request (POST, PUT, DELETE) requires this 2-step flow:

1
GET /sanctum/csrf-cookie — ask Laravel to set the XSRF-TOKEN cookie
2
Read the cookie — extract the token value from the saved cookie file
3
POST /api/login (or register, etc.) — send the token as X-XSRF-TOKEN header

Step 1 — Get the CSRF cookie

curl -s -c cookies.txt \
  -H "Origin: http://127.0.0.1:8000" \
  http://127.0.0.1:8000/sanctum/csrf-cookie
→-s — silent mode, hides download progress stats
→-c cookies.txt — save any cookies the server sends into a file called cookies.txt
→-H "Origin: ..." — tells Sanctum this request is from a known stateful domain. Without this, Sanctum does not start a session and the next request fails with "Session store not set on request"
→After this, cookies.txt contains both XSRF-TOKEN and laravel_session cookies

Step 2 — Extract the token (URL-decode it)

XSRF=$(grep XSRF-TOKEN cookies.txt | awk '{print $7}' | sed 's/%3D/=/g; s/%2B/+/g; s/%2F/\//g')
→grep XSRF-TOKEN cookies.txt — find the line with the token in the file
→awk '{print $7}' — grab the 7th column (the token value)
→sed 's/%3D/=/g' — URL-decode: the cookie is URL-encoded, %3D means =, %2B means +, %2F means /. Laravel validates the raw token, not the URL-encoded version.
→The result is stored in a shell variable $XSRF
In a real browser this decoding is done automatically by JavaScript. In curl we have to do it manually — that's why the curl flow is more complex than what happens in the browser.

Step 3 — Register a user

curl -s -b cookies.txt -c cookies.txt \
  -X POST http://127.0.0.1:8000/api/register \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -H "Origin: http://127.0.0.1:8000" \
  -H "X-XSRF-TOKEN: $XSRF" \
  -d '{"email":"krystian@test.com","password":"Artikula!2026"}' | json_pp
→-b cookies.txt — send the cookies we saved earlier (session + XSRF)
→-c cookies.txt — also save any new cookies the server sends back (session regenerates after login)
→-X POST — this is a POST request
→-H "Content-Type: application/json" — tells the server the body is JSON
→-H "Accept: application/json" — tells Laravel to return JSON errors instead of HTML redirects
→-H "X-XSRF-TOKEN: $XSRF" — the CSRF token we extracted. Laravel checks this matches the session.
→-d '{...}' — the request body (email + password)
→| json_pp — pipe the response through json_pp to pretty-print it

Why we must refresh the XSRF token before each request

After register/login, Laravel calls session()->regenerate() — it creates a new session ID and a new CSRF token. The old $XSRF variable is no longer valid. We must re-extract it from cookies.txt before the next POST.

Part 3 — Automated PHPUnit tests

Run with: php artisan test

All tests use RefreshDatabase — the database is wiped and rebuilt between every single test. Tests never affect each other.

Tests run on SQLite in-memory — fast and isolated from your real MySQL database.

File: tests/Feature/AuthTest.php

test_user_can_register PASS 
$response = $this->withHeader('Origin', 'http://localhost')
    ->postJson('/api/register', [
        'email'    => 'test@test.com',
        'password' => 'Artikula!2026',
    ]);

$response->assertStatus(201)
         ->assertJsonPath('user.email', 'test@test.com')
         ->assertJsonMissingPath('user.password');

What each line does:

→withHeader('Origin', ...) — same as adding -H "Origin" in curl. Required for Sanctum to init a session in tests.
→postJson('/api/register', [...]) — sends a POST request with JSON body. Laravel's test client handles CSRF automatically.
→assertStatus(201) — checks the HTTP status code is 201 Created
→assertJsonPath('user.email', 'test@test.com') — checks the JSON response contains {"user": {"email": "test@test.com"}}
→assertJsonMissingPath('user.password') — confirms the password hash is NOT returned in the response (security)
test_register_requires_strong_password PASS 
$response = $this->withHeader('Origin', 'http://localhost')
    ->postJson('/api/register', [
        'email'    => 'test@test.com',
        'password' => '123',
    ]);

$response->assertStatus(422)
         ->assertJsonValidationErrors(['password']);
→assertStatus(422) — Unprocessable Entity, meaning validation failed
→assertJsonValidationErrors(['password']) — confirms the error is about the password field specifically
OWASP A07 — Identification and Authentication Failures: weak passwords rejected by Password::min(8)->uncompromised()
test_register_requires_unique_email PASS 
User::factory()->create(['email' => 'test@test.com']);

$response = $this->withHeader('Origin', 'http://localhost')
    ->postJson('/api/register', [
        'email'    => 'test@test.com',
        'password' => 'Artikula!2026',
    ]);

$response->assertStatus(422)
         ->assertJsonValidationErrors(['email']);
→User::factory()->create([...]) — creates a user directly in the test database (bypasses the API). factory() uses database/factories/UserFactory.php to generate realistic fake data.
→Then we try to register with the same email — it should fail with a validation error on the email field
test_user_can_login PASS 
User::factory()->create([
    'email'    => 'test@test.com',
    'password' => bcrypt('Artikula!2026'),
]);

$response = $this->withHeader('Origin', 'http://localhost')
    ->postJson('/api/login', [
        'email'    => 'test@test.com',
        'password' => 'Artikula!2026',
    ]);

$response->assertStatus(200)
         ->assertJsonPath('user.email', 'test@test.com');
→bcrypt('Artikula!2026') — stores a hashed password. We cannot store plain text — Laravel's Auth::attempt() compares using bcrypt internally.
test_login_fails_with_wrong_password PASS 
$response->assertStatus(401)
         ->assertJsonPath('message', 'Nieprawidlowe dane logowania.');
→Checks the error message is generic — it does NOT say "user not found" or "wrong password". Both cases return the same message.
OWASP A07 — generic error prevents attacker from knowing whether the email exists in the database
test_unauthenticated_cannot_access_appointments PASS 
$response = $this->getJson('/api/appointments');
$response->assertStatus(401);
→No actingAs() — the request has no session. Laravel should return 401, not redirect to a login page.
OWASP A10 — Server-Side Request Forgery / broken auth: API always returns JSON 401, never HTML redirects

File: tests/Feature/AppointmentTest.php

All appointment tests share a setUp() method that runs before each test:

protected function setUp(): void
{
    parent::setUp();
    $this->user    = User::factory()->create();
    $this->service = Service::create(['name' => 'Terapia jakania']);
}
→parent::setUp() — runs Laravel's own setup (including RefreshDatabase to wipe the DB)
→Creates one test user and one service that all tests in this file can use via $this->user and $this->service
test_user_can_create_appointment PASS 
$response = $this->actingAs($this->user)->postJson('/api/appointments', [
    'service_id'   => $this->service->id,
    'patient_name' => 'Jan Kowalski',
    'date'         => '2026-08-01',
    'time'         => '09:00',
    'mode'         => 'stacjonarnie',
]);

$response->assertStatus(201)
         ->assertJsonPath('patient_name', 'Jan Kowalski')
         ->assertJsonPath('user_id', $this->user->id);
→actingAs($this->user) — tells Laravel "treat this request as coming from this user". Bypasses the login flow. The session and cookies are set up automatically.
→assertJsonPath('user_id', $this->user->id) — confirms the server attached the correct user_id, even though we did not send it in the request body (the controller sets it from the session)
test_user_sees_only_own_appointments PASS 
$otherUser = User::factory()->create();

Appointment::create(['user_id' => $this->user->id,    'patient_name' => 'Moj pacjent',  ...]);
Appointment::create(['user_id' => $otherUser->id,     'patient_name' => 'Cudzy pacjent', ...]);

$response = $this->actingAs($this->user)->getJson('/api/appointments');

$response->assertStatus(200)
         ->assertJsonCount(1)
         ->assertJsonPath('0.patient_name', 'Moj pacjent');
→We create 2 appointments — one for our user, one for a different user
→assertJsonCount(1) — the response array must have exactly 1 item (not 2)
→assertJsonPath('0.patient_name', 'Moj pacjent') — the first (index 0) item must be OUR appointment, not the other user's
test_cannot_update_others_appointment PASS 
$otherUser   = User::factory()->create();
$appointment = Appointment::create(['user_id' => $otherUser->id, 'patient_name' => 'Cudzy pacjent', ...]);

$response = $this->actingAs($this->user)
    ->putJson("/api/appointments/{$appointment->id}", [
        'patient_name' => 'HAKER BYL TU',
    ]);

$response->assertStatus(403);
$this->assertDatabaseHas('appointments', ['patient_name' => 'Cudzy pacjent']);
→We log in as $this->user but try to edit an appointment that belongs to $otherUser
→assertStatus(403) — Forbidden. AppointmentPolicy checks $user->id === $appointment->user_id and returns false.
→assertDatabaseHas('appointments', ['patient_name' => 'Cudzy pacjent']) — the original name is still in the database, unchanged
OWASP A01 — Broken Access Control / IDOR (Insecure Direct Object Reference): changing the ID in the URL to access another user's resource is blocked
test_cannot_book_past_date PASS 
$response = $this->actingAs($this->user)->postJson('/api/appointments', [
    ...
    'date' => '2020-01-01',
    ...
]);

$response->assertStatus(422)

test_cannot_double_book_same_slot PASS 
Appointment::create([..., 'date' => '2026-08-01', 'time' => '09:00', ...]);

$response = $this->actingAs($this->user)->postJson('/api/appointments', [
    ..., 'date' => '2026-08-01', 'time' => '09:00', ...
]);

$response->assertStatus(422)
         ->assertJsonValidationErrors(['time']);
→First we create an appointment at 09:00. Then we try to book another appointment at the same date and time — it must be rejected.
→The check happens in withValidator() in StoreAppointmentRequest: Appointment::where('date', ...)->where('time', ...)->exists()
test_cannot_book_invalid_time PASS 
$response = $this->actingAs($this->user)->postJson('/api/appointments', [
    ..., 'time' => '23:00', ...
]);

$response->assertStatus(422)
         ->assertJsonValidationErrors(['time']);
→Rule::in(['09:00', '10:00', '11:00', '13:00', '15:00', '18:00']) — only these 6 times are accepted. 23:00 is not in the list.
test_cannot_exceed_appointment_limit PASS 
foreach (['09:00', '10:00', '11:00'] as $time) {
    Appointment::create(['user_id' => $this->user->id, ..., 'time' => $time, ...]);
}

$response = $this->actingAs($this->user)->postJson('/api/appointments', [
    ..., 'date' => '2026-08-02', 'time' => '09:00', ...
]);

$response->assertStatus(422)
         ->assertJsonValidationErrors(['limit']);
→foreach — creates exactly 3 appointments (the maximum allowed)
→The 4th attempt — on a completely different date — must be rejected with a limit error
→Backend check: Appointment::where('user_id', auth()->id())->count() >= 3
